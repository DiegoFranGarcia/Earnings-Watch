# 2026-11-21: the nightly build stopped on a test that ran too early

**Summary.** The scheduled `dbt_build` failed at 06:08 UTC on two relationship tests and, as
designed, published nothing: the site kept the previous day's correct export. Two faults combined:
the tests ran before the tables they check had been rebuilt, and a company had dropped out of the
screener overnight with no new data, because the screener's window was counted from the calendar
rather than from the data. Both were fixed the same day (PR #34) and proven on the host.

## Impact

- **No wrong data was published.** The site served the 2026-11-20 export, correct but a day old,
  until a by-hand publish at 12:55 UTC, instead of the nightly run's export.
- No data was lost; nothing in RAW was involved.

## Causes

**1. Tests ran before the tables they check.** Cosmos runs each dbt model as an Airflow task and
then that model's tests (`dbt test --select export_screener`). dbt selects tests eagerly: a test
is included if any of its models is selected, so the relationship tests defined on the two company
exports ("every company here is in the screener") ran as soon as the screener was rebuilt, against
the company exports from the day before, which had not been rebuilt yet.

**2. The screener changed with the calendar, not the data.** "Still filing" meant a quarter known
within 18 months of `current_date()`. Snowflake's session time zone is America/Los_Angeles, so at
the 06:05 UTC build `current_date()` was 2026-11-20, and a company whose latest quarter became
known on 2025-05-19 fell outside the window overnight, though no new SEC data had arrived.

The order fails a build only on a day a company leaves the screener; the calendar-based window made
that happen on a day with no new data. Each is wrong on its own, so both were fixed.

## What held

- `publish` runs only if every task before it succeeded, and it is the only task that announces
  new marts, so a failed test stopped the site from receiving anything.
- The alert arrived as the retry failed, at 06:08, and named the task.
- The test that caught the empty screener during recovery (`site_exports_are_not_empty`) exists
  for exactly that case.

## Fixes (PR #34)

- Tests with more than one parent model now run as their own tasks, after all their parents
  (Cosmos `should_detach_multiple_parents_tests`), all before `publish`. A DAG test checks the
  order and fails without the setting (`tests/dags/test_dbt_build_order.py`).
- The screener's window counts back from the newest data in the warehouse (`max(known_at)`), so
  every build of the same data gives the same companies. A dbt unit test checks it.
- Accepted trade-off: a failing multi-parent test no longer stops the models after it in
  Snowflake, only `publish`; the site is protected either way.

## Lessons and follow-ups

- **`dbt build --empty` writes.** It materializes every selected model with no rows. To run a
  model's query without writing, use `dbt show`; to check it compiles, `dbt compile`.
- Diagnosing before changing anything (the runbook's rule for a failed build) found both causes
  from the failing rows themselves.
- The by-hand diagnostic runs are recorded in `AUDIT.DBT_RESULTS` like Airflow's (`run_label`
  `manual`) and count in the pipeline-health figures for the day. The Pipeline page will count
  Airflow runs only.
