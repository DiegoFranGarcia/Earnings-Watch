# 2026-11-05: a day of EDGAR's daily index was never landed

**Summary.** The run that should have landed EDGAR's daily index for Thursday 2026-11-05 failed on
all its tries, because the AWS login on the laptop that then ran Airflow had expired. Alerts did
not exist yet, and the runs after it each fetched only their own day, so the day stayed missing
for two weeks, until a manual reconciliation found it on 2026-11-21. It was repaired the same
evening through the normal pipeline, and `sec_daily_index` now checks every morning that recent
days have landed.

## Impact

- From 2026-11-06 to 2026-11-21 the warehouse lacked the 4,165 filings EDGAR accepted on
  2026-11-05, in the third-quarter 10-Q season: the 2026 filing-timeliness figures were missing
  them. The earnings-quality and restatement figures come from the SEC's quarterly data sets and
  were not affected.
- The volume gate did not notice, by design: it checks only the newest day.

## Timeline (UTC)

| Time | What happened |

| 11-06 03:05 | EDGAR publishes `master.20261105.idx` (483 KB), on time. |
| 11-06 06:06 | `sec_daily_index` (`scheduled__2026-11-06T06:00:00+00:00`), on the laptop, starts `land_index` for 2026-11-05. It fails: "Refreshing temporary credentials failed during mandatory refresh period". |
| 11-06 10:10 | The ninth and last try fails the same way. No alert: Discord alerts were added on 11-08. |
| 11-07 06:42 | 2026-11-06 is landed. Nothing returns to 2026-11-05. |
| 11-13 19:37 | The EC2 host's first boot; from 11-14 it runs the pipeline, with an instance role and no login to expire. |
| 11-21 22:18 | While measuring the README's numbers, `scripts/reconcile_bronze.py` lists 2026-11-05 as a business day with no index (a warning). EDGAR's folder shows the file. |
| 11-21 22:30 | A run with the failed run's logical date lands the day (493,703 bytes). The month's reload, `dbt_build` and the site follow by themselves; the site is redeployed at 22:40, its live check green. |

## Causes

**1. The task could not reach S3.** Every try failed in botocore while refreshing the `aws login`
session's credentials, which had expired overnight. Retries help with brief problems; this one
lasted until a person logged in again, longer than the four hours of retries.

**2. Nothing goes back to a day whose run failed.** Each run fetches the day before its logical
date. Once a run has failed for good, Airflow never reruns it, and the next run fetches its own
day. (`catchup` would not have helped: it creates runs that never existed, and this run existed
and failed.)

**3. The only check that could see the gap was run by hand.** `scripts/reconcile_bronze.py` reports
missing business days, as a warning, when someone runs it.

## Proof

- EDGAR's folder listing: the file, 483 KB, last modified 2026-11-05 10:05:27 PM Eastern.
- The laptop's Airflow database: the scheduler ran without a break from 10-30 to 11-06 23:55, so
  the run was created on time; it is recorded `failed`, from 06:06:28 to 10:10:22.
- The task's logs (`attempt=1.log` to `attempt=9.log`): each try ends with the botocore
  credentials warning above, then "Task failed with exception".
- The EC2 host's journal starts at its first boot, 2026-11-13 19:37 UTC: it was not yet running
  the pipeline.

## Repair

Triggered `sec_daily_index` as `manual__repair-2026-11-05` with `--logical-date
2026-11-06T06:00:00+00:00`, so it fetched 2026-11-05. It landed the file with its receipt, wrote
silver and announced the day; `snowflake_load_daily_index` replaced November, `dbt_build` passed,
and `publish_site` deployed the site. Afterwards `RAW.DAILY_INDEX` held 4,165 filings for
2026-11-05 (5,593 index rows), and the reconciliation showed 469 of 472 business days, the three
missing ones all days EDGAR was closed (2025-01-09, 2025-12-24, 2025-12-26).

## Fix

- Already in place before the incident was found: the host's instance role (no login to expire)
  and Discord alerts for every task that fails for good.
- New: `check_landed_days`, the last task of `sec_daily_index`. Every morning, whatever happened
  to that day's landing, it lists bronze once and fails, alerting, while a business day of the last
  four weeks has no index and was not a day EDGAR was closed (`dbt/seeds/sec_closed_days.csv`, the
  list the timeliness models use). It reads only S3, and has no outlet: a gap never holds back
  today's data. The alert repeats every morning until the day is repaired. Repairing stays a
  person's decision (runbook: *A day of the daily index is missing*).

## Lessons

- Check what landed, not only what ran: a check on the data catches a run that failed and one that
  never started alike.
- An alert raised once can be missed; one that repeats until the cause is gone cannot be for long.
