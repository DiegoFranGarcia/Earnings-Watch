# 17. Serve a static site, rebuilt by the pipeline

## Context

The project needs a public face: the dbt docs now, the Stage 9 dashboard next. Three ways to
serve them were considered:

- **A Streamlit app on the Airflow host**, as SVC_STREAMLIT was created for. The host is awake
  only from 05:45 to 09:45 UTC (ADR 12), so the app would be down most of the day; keeping it
  up would multiply the host's cost.
- **A hosted app querying Snowflake** (Streamlit Community Cloud, say). Every visitor would
  wake a warehouse and spend credits, and a Snowflake credential would live with a third party.
- **Static files, regenerated by the pipeline.** The data changes at most once a day, after
  `dbt_build`; between builds, every visitor sees the same thing.

## Decision

- The site is static and served by GitHub Pages, at no cost, with no server and no credential
  of ours exposed to a visitor.
- The pipeline builds what the site shows. The `publish_site` DAG runs on `Asset("marts")`,
  which `dbt_build` updates only after the volume gate, every model and every test passed: the
  circuit breaker (ADR 10) covers the site too. Data the pipeline held back never reaches it.
- Each export is immutable: its own folder `exports/site/runs/<run>/`, its manifest (each
  file's size and sha256), then `exports/site/current.json`, written last as the pointer. A
  half-written export is never pointed at; an older one can be redeployed to roll back.
- One workflow, `site.yml`, deploys the site. It is the only one, because a repository has
  exactly one Pages site. It runs in the `github-pages` environment, which only `main` may deploy
  to; only jobs in that environment can assume `gha-site`, which can read nothing but
  `exports/site/`. It checks every file against the manifest before deploying, and stops on
  anything unexpected, leaving the live site as it was.
- The DAG starts the workflow at once with `workflow_dispatch`, using a fine-grained token
  limited to this repository with only Actions: write, read from Secrets Manager when the task
  runs. A daily schedule at 10:30 UTC deploys the latest export anyway, so a failed dispatch
  delays the site by hours at most, and the failure alerts.
- Files are budgeted at 20 MB each, enforced when exporting and again when deploying.

## Consequences

- The site is at most a day old, and says how old: the landing page shows the export's time,
  and `site.json` records which export is live, for monitoring.
- Hosting costs nothing. GitHub's limits (a 1 GB site, a soft 100 GB of bandwidth a month, a
  10-minute deployment) are far above what this needs; the dbt docs are about 3 MB.
- The token is one more secret to rotate before it expires (the runbook has the date and the
  steps). A GitHub App would issue short-lived tokens instead, at the cost of more setup; it is
  the upgrade if a second workflow ever needs dispatching.
- GitHub disables the schedule of a public repository after 60 days without activity. The
  DAG's dispatch does not depend on it, but the fallback does: re-enable it if that happens.
- The site shows only public SEC data and the project's own models. The release's commit is
  shown; the AWS account ID in the image name is not.
